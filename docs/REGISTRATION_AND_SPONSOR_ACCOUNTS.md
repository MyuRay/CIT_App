# 学生登録の制限とスポンサーアカウント案

更新: 2026-09-17

## 今回の実装・確認

学生の新規登録は `@chibatech.ac.jp` のみ。画面・メールリンク送信・登録完了処理は `AppConstants` の同じ判定を使う。既存の `@s.chibakoudai.jp` / `@p.chibakoudai.jp` アカウントは引き続きログインできる。

ドメイン判定を末尾一致から、`@` が1個であることとドメイン全体の一致に変更した。複数の `@`、サブドメイン、似たドメイン、空のローカル部、内部の空白・改行を拒否する。入力前後の空白はアプリで除去し、大小文字は区別しない。ローカル部の許可文字は既存仕様の半角英数字と `. _ + -`。

Firebase の登録前関数 `requireVerifiedEmailBeforeCreate` が使う `functions/verified_registration.js` も同じドメイン・許可文字に統一した。本人確認済みであることは Firebase Auth の `emailVerified` で判定する。外部メールに `role: sponsor` などの値を付けても学生登録の例外にはしない。

### 検証結果

- Flutter: ドメイン・登録サービス・既存の認証状態テスト26件成功。
- Node: 登録前関数のテスト22件成功。
- アプリと関数で共有する19ケースの入力データ: `test/fixtures/registration_email_policy.json`。
- 対象 Dart ファイルの静的解析: 指摘なし。
- 2026-09-17に本番 `cit-app-2de1c` の登録前チェック・メールリンク認証・認証用Hostingを反映。本番APIの一時テストアカウントで登録・パスワードログイン・不正登録拒否を確認し、テストアカウントを削除済み。実利用者の削除・招待メール送信は行っていない。

### 本番反映と今後の確認

アプリ内のチェックだけでは Firebase Auth API への直接の登録要求を制限できないため、登録前関数を本番に反映し、Auth のブロッキングトリガーも確認済み。

Firebase Authentication with Identity Platformへ切り替え済み。旧方式のメール確認前登録は拒否されるため、新規登録にはメールリンク方式のアプリが必要。既存利用者の通常ログインは維持する。実メール受信と端末のリンク起動は別途確認する。反映手順、Gen 2フックURL修復、本番テストは `docs/EMAIL_REGISTRATION.md` を参照。

公式仕様: [Auth blocking triggers](https://firebase.google.com/docs/functions/auth-blocking-events)

## スポンサー用ログインの推奨案（未実装）

ログインIDは担当者の会社メールアドレスとし、運営が招待した人だけ利用できるようにする。担当者ごとに個別アカウントを発行し、同じ企業IDに所属させる。担当者の交代・退職時には該当アカウントだけを停止できる。

利用画面はスポンサー専用入口に分ける。一般学生の登録フォームの許可ドメインは広げず、大学メールを架空に発行したり学生のアカウントを貸したりしない。現在のログイン処理と Firestore / Storage ルールは大学メールを前提としているため、Firebase Console で外部メールのユーザーを追加するだけでは利用できない。

### 最初の提供範囲

| 操作 | スポンサー担当者 | 運営 |
| --- | --- | --- |
| 自社の広告・掲示板原稿、画像の作成・編集 | 可 | 可 |
| 原稿のプレビュー・審査申請 | 可 | 可 |
| 金色の枠、掲載期間・表示場所・公開の確定 | 不可 | 可 |
| 自社広告の表示回数・クリック数などの集計確認 | 可 | 可 |
| 他社の原稿・実績の閲覧 | 不可 | 可 |
| 学生のプロフィール・出欠・問い合わせ等の閲覧 | 不可 | 既存権限の範囲 |
| 担当者の招待・停止 | 不可 | 可 |

公開済み原稿の修正は新しい審査用の版として保存し、承認まで現在の掲載内容を維持する。スポンサーに提示する数値は、取得済みで定義が明確な集計のみとし、学生の個人データは含めない。現在の Analytics イベントだけでスポンサー別レポートが自動完成するわけではなく、企業ID・広告IDに対応した集計処理が別途必要。

### 利用の流れ

1. 運営が企業と担当者の会社メールを登録し、有効期限付きの招待を発行する。
2. 担当者がメールで本人確認し、自分の認証情報を設定する。運営が平文パスワードを配布・保管する運用は避ける。
3. ログインすると自社の原稿、掲載状況、実績だけを表示する。
4. 原稿を申請し、運営の承認後に公開する。
5. 契約終了・担当変更時は所属を無効にし、セッションも失効させる。

### 実装時の境界

- サーバーだけが招待・所属企業・権限を設定する。例として `role: sponsor` と `sponsorId` を Auth のカスタムクレームで扱い、所属の有効状態はサーバー管理データでも確認する。
- 学生用 `users` や `admin_permissions` にスポンサー自身が権限を書き込む設計にはしない。既存の `isAdmin` は付与しない。
- 学生用の公開登録とスポンサー用の招待登録を分ける。スポンサー登録を追加する際は、登録前関数でサーバー管理の有効な招待とメール所有の確認を行う経路を用意する。会社ドメイン全体やクライアントが指定した役割による例外は作らない。
- 自社だけを扱える条件を画面・サーバーAPI・Firestore / Storage ルールのすべてに実装する。企業IDをURLや送信データで書き換えても他社にアクセスできないことをテストする。
- 掲載操作はサーバーで運営権限を再確認し、企業・対象原稿・操作者・日時の履歴を残す。
- 招待なし、期限切れ、停止済み、他社ID指定、学生データへのアクセス、自己昇格を拒否する結合テストを実施してからIDを提供する。

Firebase のカスタムクレームは Admin SDK を使う信頼できるサーバーで設定し、セキュリティルール等で確認できる。
公式仕様: [Control Access with Custom Claims and Security Rules](https://firebase.google.com/docs/auth/admin/custom-claims)
